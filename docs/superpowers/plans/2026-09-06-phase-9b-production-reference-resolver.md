# Phase 9B Production Reference Resolver Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build a deterministic, fail-closed, read-only production reference resolver that consumes a Phase 9A-valid and ready `CatalogPackV1`, resolves production catalog/reference UUIDs without writes, and emits a stable `ResolvedCatalogManifestV1`.

**Architecture:** Keep Phase 9B under `scripts/catalog-pack/`. Phase 9A validation remains the first gate; a narrow `CatalogReferenceReader` loads a whitelisted production snapshot using SELECT-only access; a pure resolver performs exact code resolution, recipe-tag adaptation, identity/version collision classification, deterministic sorting, and snapshot hashing; a Node 24 CLI orchestrates the flow and never exposes a mutation API.

**Tech Stack:** Node 24, TypeScript strict mode, `@supabase/supabase-js` 2.x, existing Phase 9A catalog-pack modules, existing `canonicalUtf8`, Node `crypto`/`fs`, Vitest 4.

**Spec:** `docs/superpowers/specs/2026-09-06-phase-9b-production-reference-resolver-design.md`

## Global Constraints

- Phase 9B is read-only: no insert, upsert, update, delete, publish, retire, migration, deployment, or production catalog mutation.
- The Supabase adapter uses only table `.select(...)` calls and read filters on the approved Phase 9B table whitelist; Phase 9B calls no Supabase RPC.
- The CLI must run Phase 9A validation first and perform zero production queries unless the input is both `valid` and `ready`.
- Exact logical-code matching only; no fuzzy, partial, translated-name, case-insensitive, prefix, suffix, fallback, or nearest-code resolution.
- Missing production identities are represented with `id: null`; Phase 9B never fabricates UUIDs.
- Existing requested version numbers are blocking `VERSION_ALREADY_EXISTS` diagnostics; do not overwrite, reuse, republish, or auto-increment versions.
- Static/reference drift, identity conflicts, and ambiguous recipe semantic tags fail closed.
- Production UUIDs, revisions, and statuses may appear in the resolved operational manifest; secrets, Supabase URL, bearer tokens, passwords, vendor error text, timestamps generated by the resolver, and query metadata must not.
- No household, auth-profile, pantry, shopping-list, meal-plan, or other user/private data may be queried.
- Normal CI remains offline and deterministic; a live production read smoke check is optional and is never a normal CI requirement.
- Do not import `catalog-pack-test-builder.ts` or any Phase 9B test builder from runtime CLI/reader/resolver modules.
- Work remains on `codex/phase-9b-production-reference-resolver`; no PR, merge, production write, migration, or deployment is part of this plan.

- [ ] **Step 3: Implement identity compatibility and version classification**

Add helpers with these exact semantics:

```ts
function classifyVersion(
  parentId: string | null,
  requestedVersionNumber: number,
  rows: readonly ProductionVersionRow[]
): ResolvedIdentityVersion["version"] {
  if (parentId === null) {
    return { state: "pending_parent_creation", id: null, revision: null, publicationStatus: null }
  }
  const matches = rows.filter(
    (row) => row.parentId === parentId && row.versionNumber === requestedVersionNumber
  )
  if (matches.length === 0) {
    return { state: "missing", id: null, revision: null, publicationStatus: null }
  }
  const row = matches[0]!
  return {
    state: "collision",
    id: row.id,
    revision: row.revision,
    publicationStatus: row.publicationStatus
  }
}
```

For foods, an existing identity is compatible only when all are exact: `code`, `nameVi`, `baseDimension`, resolved `baseUnitId`, not retired. For recipes and meal options: exact `code`, exact `nameVi`, not retired. Any mismatch/retired row becomes `conflict` and adds `IDENTITY_CONFLICT`.

If more than one snapshot identity row has the same logical code, fail closed with `IDENTITY_CONFLICT`; do not pick one.

Every `collision` adds `VERSION_ALREADY_EXISTS`, including price books. Missing versions are allowed. Child versions of missing parents remain `pending_parent_creation`.

Create `supabase-catalog-production-reader.ts`:

```ts
import { createClient, type SupabaseClient } from "@supabase/supabase-js"
import type { Database } from "../../src/infrastructure/supabase/database.types.ts"
import {
  createCatalogProductionReader,
  type CatalogReferenceReader,
  type CatalogSelectGateway,
  type CatalogSelectRequest
} from "./catalog-production-reader.ts"

function applyFilters(query: any, request: CatalogSelectRequest): any {
  return request.filters.reduce((current, filter) =>
    filter.operation === "eq"
      ? current.eq(filter.column, filter.value)
      : current.in(filter.column, [...(filter.value as readonly (string | number)[])]), query)
}

export function createSupabaseCatalogSelectGateway(
  client: SupabaseClient<Database>
): CatalogSelectGateway {
  return {
    async select(request) {
      const initial = client.from(request.table).select(request.columns)
      const { data, error } = await applyFilters(initial, request)
      return error === null && Array.isArray(data)
        ? { ok: true, rows: data }
        : { ok: false }
    }
  }
}

export function createSupabaseCatalogProductionReader(
  client: SupabaseClient<Database>
): CatalogReferenceReader {
  return createCatalogProductionReader(createSupabaseCatalogSelectGateway(client))
}

export function createRuntimeCatalogProductionReader(env: NodeJS.ProcessEnv): CatalogReferenceReader | null {
  const url = env.SUPABASE_URL
  const secretKey = env.SUPABASE_SECRET_KEY
  if (url === undefined || secretKey === undefined || url.length === 0 || secretKey.length === 0) return null
  const client = createClient<Database>(url, secretKey, {
    auth: { autoRefreshToken: false, detectSessionInUrl: false, persistSession: false }
  })
  return createSupabaseCatalogProductionReader(client)
}
```

Do not widen the client to `any`; the `applyFilters` query-helper may use the narrowest local structural type needed by Supabase's builder.

There must be no `.rpc(`, `.insert(`, `.upsert(`, `.update(`, or `.delete(` in this file.
